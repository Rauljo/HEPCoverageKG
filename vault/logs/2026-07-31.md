# 2026-07-31 — the query layer answers a real question, correctly

## The headline

```
"How many analyses used Pythia?"
  search -> set_1 (56 entities)
  count(sample_uses_generator, set_1)
  -> 58 papers / 344 facts / 367 assertions
```

Matches ground truth **exactly**, 100% of claims grounded, 202 evidence quotes, **6 seconds**.
**280 tests.** First end-to-end answer from the system.

## Built

- **`retrieve.py`** — words → entity sets. 8,449 surface forms for 5,114 entities (every wording,
  from `entity_occurrence`, plus 3,109 aliases — `hepkg:object:jet` alone has **40 spellings**).
  Hybrid: BM25 (written here, because the tokeniser is domain-specific — a generic splitter destroys
  `b-jet`, `13 TeV`, `PYTHIA 8.212`) fused with dense embeddings **by rank, not score** (cosine sits
  in a narrow band, BM25 is unbounded; a weighted sum needs a calibration that shifts with the
  corpus). Deduped by canonical cluster.
- **`planner.py`** — nine tools, batched calls, budgets, guards, the trace.
- **`verify.py`** — mechanical faithfulness. Every number and id in an answer must appear in a row
  that was actually returned.
- **`graph.py`** — the loop as a LangGraph state machine. **S-16 fulfilled.**

## Four failure modes, found live, each hiding the next

1. **wrong answer** — *"the graph records no analyses that used Pythia"* (truth: 58)
2. → `count` got a **fabricated id**, `gen-223`
3. → because the model **batched `search` and `count` in one round**, writing `count` before any ids
   existed. Guard added: ids must have been returned by the graph this session.
4. → the model then **corrected itself perfectly** — right predicate, right ids — but wrote the call
   as **text**, which vLLM's parser missed and the loop mistook for "answered in prose".
5. → recovery added; it still failed, because the text was **truncated at 6,521 characters**,
   mid-identifier. It had looped writing ids until the cap.

Only at (5) does the real cause appear: **making the model retype 31 long identifiers** — 863
completion tokens for one call. Fixed by **named sets** (S-29).

*The most instructive part*: at step (1) the trace looked **healthy** — grounded in tools, no errors,
no nudge, faithfulness clean, because an answer containing no numbers has nothing to check.
**A wrong answer wearing a good trace** is the shape to watch for.

## Hardware: one A100 is failing (D-040)

`00000000:CA:00.0` on compute-gpu-0-1 dies with `uncorrectable ECC error encountered` on the **first
inference request**. Reproduced twice (jobs 48125, 48128), both at `rank=1`, both ~5 minutes in.
**27 → 40 uncorrectable ECC errors within two hours of a reboot** (805 → 818 aggregate), 8 remapped
rows, and `remapped_rows.failure=1` with `pending=0` — the card tried to retire bad memory and
**could not**, and nothing awaits a reset, so a reboot cannot fix it. It did not.
Reported to the cluster admin, who had already drained the node. Now serving **TP=1** on a healthy
card with a **bus-id** guard that exits in ten seconds on a bad draw.
*Guard bug worth remembering*: the first version checked **every card in the box**, because
`nvidia-smi` ignores `CUDA_VISIBLE_DEVICES` — it refused job 48129, which held a clean GPU. Fixed
with `-i`.
*Not our doing*: software cannot cause uncorrectable ECC errors, and eight retired rows are a
long-term degradation. Heavy sustained use **exposed** a latent fault. And no silent corruption is
possible — uncorrectable means *detected*, so CUDA aborts rather than returning wrong values. The
2026-07-29/30 Qwen trial results stand.

## Decided

- **S-29** — the model never handles entity ids; `search` saves a named set. 122s → 6s,
  863 → 139 completion tokens, wrong answer → right one. Unexpected second payoff: sets are the unit
  of **memory** across turns.
- **S-30** — state describes the run, config carries the machinery. Checkpointing forces plain
  serialisable state, learned three times in ten minutes.
- **S-31** — compaction and recall designed, deliberately **deferred** until there is a question set
  to measure them against. A first pass proposing "compact everything deterministically" was wrong:
  for `describe`/`list`/`crosstab` the rows **are** the content, and the model's reasoning cannot be
  reconstructed from a `Step`.

## Open

- **`--max-model-len` is 8192**; one question already costs **11,902 prompt tokens over 3 rounds**.
  Raise to 32k — one flag, and the card has 97k of KV cache.
- **`limit` is still exposed to the model** — the under-searching lever. `concept("Pythia", limit=6)`
  gives 45 papers; `limit=60` gives 58. The model choosing 6 would be wrong with a clean trace.
- **One reasoning failure no guard catches**: asked which systematics affect jet measurements, the
  model used `result_has_systematic` in the **wrong direction** (systematics attach to *results*, not
  to jets) and concluded nothing exists — against 1,148 rows. Not plumbing. This is what the
  evaluation is for.
