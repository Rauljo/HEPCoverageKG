# 2026-08-03 — the question tiers, and a coverage map that could not read a paper

*Continues [`2026-08-02.md`](2026-08-02.md). Long session: three question tiers built, one
missing primitive found, four measurement bugs, one bad cluster node.*

## The headline: `contents_of`

**The system could go concept -> papers and had no way to go paper -> contents.** `papers_of`
existed; nothing was its inverse. So *"which generators does analysis 2001.06899 use?"* was
unanswerable — the planner searched for the arXiv id, found nothing, then passed the id into
`describe` as if it were an entity id:

```
60 `unknown_entity_id` errors across 45 questions
answers claiming a paper "is not found in the current graph" when it plainly is
count_correct 0.06 · tool_error_rate 0.386
```

Not a tuning problem: **the operation did not exist.** And for a COVERAGE MAP the most natural
question about one paper is *"what does this analysis cover?"*, so the gap mattered to the product,
not only to the evaluation. Nobody had noticed because every question shape built so far starts from
a concept and finds papers — Tier A tested the other direction on its first run and it fell out
immediately.

After adding it (D-047):
```
count_correct 0.06 -> 0.50 · tool_error_rate 0.386 -> 0.083
answered 0.56 -> 0.85 · faithfulness 0.08 -> 0.74 · set questions: retrieval 1.00, naming 0.895
```

## Four measurement bugs, all the same mistake

**Each was a metric anchored to ONE CODE PATH rather than to the behaviour**, and each was found by
an impossible-looking number rather than by a crash.

1. **`_evidence_for` returned every evidence row in the graph.** `SELECT assertion_id FROM (<caller
   sql>)` — with no `assertion_id` in the subquery SQLite resolves the bare name against the
   *enclosing* scope, so the condition is always true. **11 rows of output, 8,369 evidence ids, no
   error.** The helper now refuses a query without that column, which protects every future template.
2. **`_collect_ids` knew only `entity_id`/`canonical_id`.** `contents_of` returns `object_id`, so
   every id it produced was rejected as invented by the guard. **`describe` had the same latent bug**
   — chaining one describe into another would have failed identically.
3. **The harness read `session.sets`**, which only `search` fills. `contents_of` scored **zero
   retrieval while the answer named 83% of the entities correctly** — an impossible pair, and the
   giveaway.
4. **`retrieved_first` counted only `search`.** It fell 1.00 -> 0.18 the moment `contents_of` existed,
   because the planner retrieved by a different route.

## Three question tiers now exist

| tier | n | truth anchored on | tests | dedup? |
|---|---|---|---|---|
| **A** per-paper | **1,352** | `paper_id`, a hard identifier | reading one paper | no |
| **B** concept counts | **436** (109 concepts) | invariance-tested concept | counting across the corpus | yes |
| **retrieval** | **720** | the entity id | can it find a thing at all | no |

**Tier A is the backbone.** A paper id is unambiguous, so the truth never moves when deduplication
changes — and it reaches the **31% of assertions stored as free-text values** (`object_has_selection`
97% values, `region_has_selection` 98%, `result_reports_quantity` 97%) that concept questions cannot
touch at all. Truth is deduplicated *within* the paper (D-046), or a region stored twice would make a
correct answer score wrong.

**Tier B** applies S-58's invariance rule, now with the merge proposals folded into the broad reading
(S-60):
```
spelling only          263 well-posed · 45% survive
spelling + proposals   109 well-posed · 19% survive
```
The drop is correct: spelling cannot see that `b-jet` and `Bottom (b)-tagged jet` are one thing, so
154 concepts were only *apparently* safe.
**Two limitations, both measured**: it selects for RARE concepts (69 of 109 appear in exactly two
papers; the largest is 20; *"how many analyses used Pythia?"* → 58 does **not** survive, because
Pythia has 56 spellings) — so it cannot yet substitute for the coverage-aggregation questions that
motivate the project. And it has **false negatives**: `SMEFT@NLO` / `SMEFTatNLO` survive as separate
concepts because neither normalised string contains the other.

**Retrieval questions** rescue what Tier B discards. A *count* depends on where the boundary is drawn;
*"did this entity come back"* does not. So all 720 concepts are testable, ambiguous or not.
599 are "hard" (<=2 papers) and **480 have a single spelling in the whole corpus** — which is exactly
where retrieval should fail and where a coverage map most needs to work.
*Caveat recorded*: difficulty is labelled by paper count, which is a **hypothesis**, not a
measurement. If failures do not concentrate in that bucket the label is wrong and should be rebuilt
on spelling count.

## The counterintuitive one: applying merges GROWS Tier B

Asked whether a *relaxed* aliases layer would give a bigger Tier B. It is the opposite — more merge
proposals widen `broad`, so more concepts disagree and **fewer** questions survive.
What grows Tier B is **confirming** correct merges: `_papers_for` expands through
`entity_canonical`, so a confirmed merge makes `narrow` and `broad` **converge** and the question
becomes well-posed.
**So the review work is not quality assurance, it is what unlocks the question set** — and the size
of the usable Tier B set becomes a direct measure of deduplication quality (S-11 with a number).

## Where the aliases funnel actually narrows

Asked whether the thin semantic half is because there are few aliases. No:
```
all possible same-kind pairs   ~1,122,162
  proposed by embeddings+Jaccard   14,656   (1.3%)
  surviving the guards              9,570
  approved                          2,262
entities never in ANY pair           1,436   (28% of the graph)
```
**Candidate generation is the bottleneck** — 98.7% of pairs were never considered, so most merges
could not be approved because they were never proposed. Three separate limiters, three different
fixes: candidate generation (feed `entity.aliases` in — already in the backlog, and `MET` /
`E_T^miss` are sitting there unused), the guards (35% vetoed), adjudication (24% approved).

## Cluster problems: a node that accepts work and does none

Two overnight jobs ran **eight hours and wrote no output file at all**. Slurm always creates one if
the script runs, so nothing ran.
```
compute-0-0  ->  srun hostname returns instantly
compute-0-1  ->  srun hostname hangs indefinitely; Slurm later says ReqNodeNotAvail
```
Same shape as the faulty A100 (D-040). Now excluded in `hpc/eval_job.sh` with the evidence in the
script. **Also**: `langgraph` was not installed in the DIAS venv, so every question died with
`ModuleNotFoundError` — that alone would have cost the night.
*The circuit breaker worked*: 20 consecutive errors, run stopped in 20 seconds instead of 8 hours.
*And then corrupted its own output*: the abort path called `_rewrite_meta` from **inside** the still
open `with` block, interleaving with the buffer and producing `{"r{"run_id":...`. A correct guard,
ruined by where it was placed. Now flagged-and-broken-out, with a test asserting an aborted run
leaves a PARSEABLE file.

## Rewording, built and validated (S-67)

Two modes with **opposite goals and opposite mechanical guards**:
```
FAITHFUL (Tier B)     keep the entity name verbatim, meaning unchanged   guard: name survived
VAGUE (retrieval)     never name the entity                              guard: no token >=4 chars leaked
```
Both guards are mechanical on purpose — "keep the name" and "do not name it" are exactly what a model
half-follows. A rewrite failing its guard is **discarded, never repaired**: a silently-drifted
question keeps the old truth and is worse than a clumsy one.
Validated live: faithful 5/5 kept; vague 2/6 with retries (~33%), so rewriting all 720 retrieval
questions should yield ~240. The low vague keep-rate is the guard doing its job — a leaked name turns
the retrieval test into string matching.
*Found while testing*: Tier B carried no readable `label` in provenance, so the rewriter was told to
preserve `hepkg:systematic:background-normalization` and pasted the identifier into the question.
