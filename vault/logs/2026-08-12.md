# 2026-08-12

## Happened

**Two JSON parser faults found, and they had been silently deleting evidence all along.**
`parse_reply` discarded 20% of the single-paper run's calls and 2.5% of the sweep's — 599 of which
were complete, well-formed answers. The extractor took the last *brace-free* object, so a quote
carrying `${\approx}4.8$` selected `{\approx}` and the reply was thrown away; and the 24B copies
LaTeX into JSON strings verbatim, where `\m` is not a legal escape. Both filters selected for replies
quoting cut values, masses and efficiencies — the content the questions ask for.

The loss was **one-directional**: 475 recovered YES, 0 recovered NO. A "no" carries no quote, so
there is no LaTeX to choke on. The bug could only ever delete evidence.

`reparse()` recovered it all from stored raw replies at no GPU cost. The conditions path did *not*
store raw replies, so gf-01 had to be re-read — that path now keeps them.

**The single-paper questions finally run the same cascade as everything else** (both models gather
every window, union, then judge), and **the judge now grades extraction questions on their VALUE**.

## Mistakes worth keeping

- Three comparisons made before one was valid, each from changing more than one thing at once:
  wrong baseline file, different judge models, and `repeats` 2 → 3.
- The value judge was written, tested, deployed and **never ran** — the CLI trimmed `provenance` off
  the questions and the routing set was always empty. The unit test passed because it called the
  function directly with full records. A test that builds its own input cannot catch a caller that
  builds a different one.
- `wait -n` is unsupported by the cluster's bash: the server script died 31 seconds in while both
  models kept serving as orphans, and Slurm reported the node idle with all three A100s free for two
  hours. Nothing downstream noticed, because the servers still answered.
