# HEPCoverageKG — Progress report (week of 2026-07-09 → 15)

**Project**: a typed knowledge graph mapping which HEP final states have been probed, by which
experiment, at which energy — to surface coverage gaps for BSM searches (MUSiC-style event
classes). Three layers: harvest published papers → extract structured fields via retrieval-
augmented LLM → build/query the knowledge graph.

This week was one infrastructure milestone plus a substantial block of design work — the
extraction baseline is running end-to-end, and the architecture for the agentic and
gap-analysis layers is now specified. No blocking issues.

---

## 1. Working software this week

**End-to-end extraction verified on a real paper.** The harvest → extract pipeline runs
against arXiv:2307.01094 (ATLAS, pair-produced squarks/gluinos → 2 same-sign or 3 leptons,
139 fb⁻¹ — analysis code **SUSY-2020-27**). From the arXiv HTML it correctly recovers the
final-state objects, centre-of-mass energy (13 TeV), integrated luminosity (139 fb⁻¹), targeted
process (SUSY), observables, and estimated backgrounds — each as a typed (subject, predicate,
object) assertion with an evidence snippet and a confidence value. Extraction is "cellular":
each field is retrieved and asked independently, so one bad field is isolated rather than
poisoning the whole record.

**Self-hosted LLM on DIAS — zero marginal cost.** Generation now runs on a self-hosted vLLM
server on the UCL DIAS A100 nodes (via Apptainer/SLURM), replacing the paid API used for
prototyping. The pipeline's LLM backend is fully swappable by configuration — self-hosted,
Groq, or any OpenAI-compatible provider — so we can never be blocked by a single provider going
down, and can drop in a frontier hosted model for a one-off comparison without code changes.

**Compute headroom confirmed empirically.** I profiled the DIAS GPUs directly. Usable ceiling
is ~158 GB per model (two A100-80GB tensor-parallel; a third card is available for a second,
smaller model). This comfortably covers the planned model-size comparison (8B → 32B → 70B);
larger frontier models are neither needed (extraction is grounding-limited, not reasoning-
limited) nor worth self-hosting. So the "does a bigger model extract better?" experiment is
fully supported once the test set exists.

## 2. Design decisions made (with rationale)

- **Knowledge-graph identity / de-duplication.** Two papers reporting the *same* final state
  connect to the *same* shared node — that multiplicity is exactly the coverage signal we
  measure. De-duplication happens on the vocabulary entities (merging, e.g., "SUSY" and
  "supersymmetry"), never on the papers themselves. Identical entities collapse automatically
  via deterministic canonical IDs; genuinely ambiguous cases go to a periodic, human-confirmed
  reconciliation step rather than being auto-merged (auto-merging is how knowledge graphs
  silently rot).
- **Open vocabulary with a safety flag.** The controlled vocabularies (processes, backgrounds)
  will allow an "other" escape hatch so a paper searching for something outside our list still
  contributes, rather than being silently dropped. For detector objects the vocabulary stays
  closed, but with a flag for "this analysis needs an object we can't express" (e.g. a
  substructure-tagged large-R jet) — because misfiling such a paper under an ordinary class
  produces a **false _covered_**, which is worse than a gap: a gap gets investigated, a false
  covered gets trusted.
- **Two lightweight verification passes, flag-only.** A cross-field consistency check
  (e.g. does the energy/luminosity pairing make sense for one dataset?) and a per-section
  "what did we miss?" pass. Both can only *flag* an assertion for review — never silently
  rewrite it — preserving the evidence trail.
- **Validation approach (Pydantic).** Decided to keep field-level validation on the way in and
  reserve whole-object schema validation for derived outputs, and to trial schema-constrained
  ("guided") decoding as a measured variant rather than adopting it blindly.

Full decision log with rejected alternatives is maintained in the repository.

## 3. Where agents fit in the pipeline (the main design thread)

The guiding principle: **agents are not added for complexity — they are a measured treatment
arm against the simple pipeline as a control.** The research question becomes "does agentic
verification/reasoning improve evidence-grounded extraction, and at what cost?" — where a
negative result is still a result. Candidate insertion points, in order of value:

1. **Extraction verification — a panel of narrow critic agents** (flag-only, feeding one
   review queue): a *fidelity* critic (does the assertion match the retrieved text?), a
   *physics-coherence* critic (grounded in a small curated physics fact-sheet), and a
   *corpus-consistency* critic (is this assertion novel relative to the existing graph?). Two
   hard design rules, both learned from the AgentRivet paper (below): critics must re-read the
   **source**, not just the extracted fields (otherwise they can't catch omissions — the
   dominant, invisible failure mode); and a critic must never *overwrite* a value, only flag it.

2. **A blocker-vs-advisory authority rule.** Anything an external source can check
   (HEPData / SimpleAnalysis / pyhf likelihoods) is a **blocker** that can overwrite the
   extractor; anything only another LLM can judge is **advisory** and can only flag. This is
   the principled reason the critics are flag-only, and it makes the physics preservation data
   load-bearing rather than decorative.

3. **A gap-hypothesis reasoning agent — the headline-results generator.** The graph enumerates
   empty (final state × experiment × energy) cells deterministically; a reasoning agent then
   evaluates which empty cells are *physically sensible and theoretically motivated* gaps
   versus trivial/forbidden ones, and — crucially — performs a **literature check** (has an
   un-ingested paper already covered this?) before proposing a gap. That literature check
   (query the graph, search InspireHEP, consult theory, synthesise) is the one place in the
   project where genuine tool-using agency is *earned* rather than decorative.

4. **Adaptive re-querying and debate-based reconciliation** as smaller, optional agentic
   components.

Sequencing is deliberate: the non-agentic baseline is built and measured first; agents are
layered on as evaluable comparisons. On compute, all of this fits DIAS provided agents *share*
a served model by role (a "physics critic" is a prompt, not a separate model) rather than each
loading its own weights.

## 4. Literature positioning

The most relevant prior system is **AgentRivet** (arXiv:2606.13535, Manchester/UCL) — a
multi-agent LLM pipeline that reads HEP papers and generates missing Rivet routines. It is the
closest existing work and validates that LLM extraction from HEP papers is feasible, but from a
*more favourable* regime: measurements carry precise fiducial definitions because Rivet demands
them, whereas the searches we target have no such discipline. Its empirical failure modes
(source ambiguity dominates over model capability; silent omission is the hardest failure to
catch) have been folded directly into our design.

There is also a clean programme-level connection worth flagging for the write-up: **Contur**'s
reach is bounded by Rivet's ~39% measurement coverage, and Rivet's missing-routine priorities
are currently hand-curated. An event-class coverage map could give a *principled* priority
ordering — i.e. this project and the AgentRivet/Contur programme point at each other. This is
also the natural answer to "how does this differ from what Contur already does?"

## 5. Open questions where physics input would help

1. **`result_type` vocabulary and its role in gap logic.** Proposed types: search /
   measurement / combination / observation. Key question: should a BSM coverage gap count only
   *search*-type results, or should measurements count differently? This gates the final
   coverage query.
2. **Final-state representation.** Whether a final state should be a single composite node
   (e.g. "2e + 1 jet + MET") or reconstructed from individual object edges — and how strictly
   to handle flavour-inclusive vs flavour-specific labels ("2 leptons" ≠ "2 electrons"). This
   is the main modelling decision before scaling up.
3. **Ground truth for evaluation.** Does SUSY-2020-27 (our test paper) have a public
   SimpleAnalysis routine or pyhf likelihood? If so, we may be able to machine-label
   reconstructed-level signal-region selections for evaluation instead of hand-labelling —
   which would materially strengthen the validation set on the *search* side.
